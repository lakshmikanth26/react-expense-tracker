# Family Finance Tracker

A fast, mobile-first expense/income tracker for a family, built with React, TypeScript,
Vite, Supabase (Postgres + Auth + Row Level Security), Tailwind CSS, and shadcn/ui.

The core product principle: **recording an expense should take one tap + an amount + save.**

## Features

- **Auth & family onboarding** — email/password or email OTP sign-in; creating an account
  walks you through naming your family and gets 23 expense categories, 6 income categories,
  and 4 default accounts (Bank, Cash, UPI, Credit Card) set up automatically.
- **Transactions** — add expense/income/transfer in a few taps, with smart defaults
  (last-used category/account/member per type) and a "recent transactions" quick-reuse strip.
  Edit, duplicate, and soft-delete are all supported.
- **Dashboard** — monthly income/expense/savings summary, month-over-month comparison, a
  trend chart, a spending-by-category donut, and up to 4 deterministic insights (e.g. "Food
  spending increased 18% vs last month").
- **Transactions list** — debounced search, filter by category/member/account/type/amount
  range/month, paginated.
- **Analytics** — category breakdown (with subcategory drill-down) and per-member spending.
- **Budgets** — monthly budgets per category or overall, with ok/warning/over status at
  80%/100% of spend.
- **Recurring transactions** — daily/weekly/monthly/yearly schedules that generate real
  transactions client-side on app load (see [Known limitations](#known-limitations)).
- **Savings goals** — target amount + progress tracking.
- **Accounts** — balances kept in sync automatically via a Postgres trigger on every
  transaction insert/update/delete, with credit cards treated as liabilities.
- **Reports & CSV export** — a date-range report with CSV download (UTF-8 BOM, so ₹ and
  Excel both behave).
- **Settings** — manage family members, categories, and accounts; delete the entire family
  (type-to-confirm, cascades everywhere).
- **Dark mode**, responsive layout (bottom nav on mobile, sidebar on desktop), and
  keyboard-focus-visible styling throughout.

## Tech stack

- **React 19 + TypeScript + Vite** — app shell, routing (`react-router-dom`), lazy-loaded routes
- **Supabase** — Postgres database, Auth (email/password + email OTP), Row Level Security
- **Prisma** — schema-authoring and migration tool only (dev-time). The app never imports
  `@prisma/client` or talks to Postgres directly; all runtime reads/writes go through
  `@supabase/supabase-js` with the anon key, and access control is enforced entirely by RLS.
- **Tailwind CSS v4 + shadcn/ui (Radix primitives)** — design system
- **TanStack Query** — server state/caching
- **Recharts** — dashboard/analytics charts
- **react-hook-form + zod** — forms and validation
- **GitHub Actions + GitHub Pages** — CI/CD

## Why Prisma *and* Supabase?

Prisma models the schema and generates/reviews migrations (`prisma/schema.prisma` →
`prisma/migrations/*/migration.sql`), run with `DATABASE_URL` / `DIRECT_URL` — a Postgres
connection string with real database credentials. That connection is **only ever used from
your machine or CI at migration time**, never from the browser.

The migrations in this repo, applied in order:

- `20260101000000_init` — tables, enums, indexes, foreign keys (generated by
  `prisma migrate diff --from-empty`)
- `20260101000001_rls_and_defaults` — hand-written SQL for everything Prisma can't express:
  foreign keys into Supabase's managed `auth.users` table, `CHECK` constraints, `updated_at`
  triggers, an account-balance-sync trigger, a `create_family_with_defaults()` RPC, and every
  Row Level Security policy.
- `20260101000002_budgets_overall_unique` — a partial unique index preventing two "overall"
  (no-category) budgets in the same month for one family — Postgres treats `NULL` as distinct
  in a plain `UNIQUE` constraint, so this needed its own index.
- `20260101000003_delete_my_family` — a `delete_my_family()` RPC for the Settings "delete
  everything" flow, which checks family membership before cascading the delete.

The running app talks to Postgres exclusively through `@supabase/supabase-js` using the
**anon key**, which PostgREST resolves against the signed-in user's JWT — RLS is what actually
restricts which rows that key can see or touch.

## Supabase setup

1. Create a project at [supabase.com](https://supabase.com).
2. Grab your project ref and database password from **Project Settings → Database**, and
   your API URL/anon key from **Project Settings → API**.
3. Copy `.env.example` to `.env` and fill in all four variables.
4. Apply the migrations:
   ```bash
   npx prisma migrate deploy
   ```
   (This runs all four `migration.sql` files above, in order, against `DIRECT_URL`.)
5. *(Optional, local/dev only)* seed a demo family with a few months of realistic
   transactions:
   ```bash
   psql "$DIRECT_URL" -f supabase/seed.sql
   ```
   Signs in as `demo@familyfinance.app` / `demopassword123`. **Never run this against a
   production project** — it inserts a row directly into `auth.users`.

### Making schema changes later

Edit `prisma/schema.prisma`, then generate the diff instead of hand-writing SQL:

```bash
npx prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --script > /tmp/next.sql
```

Review the output, drop it into a new `prisma/migrations/<timestamp>_<name>/migration.sql`,
and add any RLS policies the new tables/columns need by hand (Prisma has no concept of RLS).

## GitHub Pages deployment

`vite.config.ts` sets `base: '/react-expense-tracker/'` to match this repo's Pages URL
(`https://<username>.github.io/react-expense-tracker/`). If you fork this repo under a
different name, update `base` to match.

`.github/workflows/deploy.yml` builds and deploys automatically on every push to `main`:

1. In your GitHub repo, go to **Settings → Pages** and set **Source** to "GitHub Actions".
2. Add two **Actions secrets** (**Settings → Secrets and variables → Actions**):
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_ANON_KEY`
3. Push to `main` — the workflow builds and deploys `dist/`.

### Why deep links (e.g. `/analytics`) work after a refresh

GitHub Pages has no server-side router, so a hard refresh on `/analytics` normally 404s.
This repo uses the standard [spa-github-pages](https://github.com/rafgraph/spa-github-pages)
trick: `public/404.html` redirects to `/`, encoding the original path in the query string;
a small inline script in `index.html` decodes it back via `history.replaceState` before React
Router ever sees the URL. `react-router-dom`'s `BrowserRouter` is used with
`basename={import.meta.env.BASE_URL}`, so both dev and production resolve routes correctly.

## Troubleshooting

- **"Missing VITE_SUPABASE_URL..." on startup** — copy `.env.example` to `.env` and fill it in.
- **RLS errors ("new row violates row-level security policy")** — you're almost always
  missing a `family_id` on an insert, or the referenced category/account/member belongs to a
  different family. Check the browser console for the underlying Postgres error.
- **A route 404s after refreshing on GitHub Pages** — confirm `base` in `vite.config.ts`
  matches your repository name exactly, and that `public/404.html` deployed alongside `index.html`.

## Known limitations

- **Recurring transactions have no true backend scheduler.** This is a static-hosted SPA with
  no server, so due occurrences are generated client-side, once per family per browser
  session, when any family member has the app open (`useRecurringSync`). A family that doesn't
  open the app for a while will see all missed occurrences generated in a single catch-up
  batch next time someone does (capped at 24 occurrences per recurring rule, so a very stale
  family won't get years of backdated transactions). Nothing is ever double-generated. A real
  scheduler (Supabase cron job / Edge Function) would remove this catch-up dependency
  entirely.
- **CSV import is not implemented** — export (Reports page) works; there is no bulk-import
  flow. Adding transactions is deliberately fast enough one-at-a-time that this was
  deprioritized for the MVP.
- **Multi-currency is partial.** All formatting helpers accept a `currency` parameter and
  default to INR; there is no per-family currency setting or conversion between currencies in
  the UI yet.
- **No automated end-to-end tests.** UI flows were verified manually (dev server + a
  Playwright-driven browser, across light/dark and mobile/tablet/desktop) rather than with a
  checked-in Playwright/Cypress suite. The unit-test suite covers business logic
  (calculations, dates, insights, CSV, formatting) but not component rendering or user flows.
- **Insights are deterministic, not AI-generated** — by design (see the product spec), but
  the module (`src/lib/insights.ts`) is structured so an LLM-backed insight source could be
  added later without changing its interface.

## Next recommended improvements

1. A real recurring-transaction scheduler (Supabase cron/Edge Function) to remove the
   catch-up-on-open limitation above.
2. CSV import, reusing the same category/account/member matching logic already used for
   manual entry.
3. A checked-in Playwright suite covering the golden paths (sign up → onboarding → add
   transaction → see it on the dashboard) so UI regressions are caught in CI, not manually.
4. Per-family currency selection, if the household actually needs it.
5. Push notifications/reminders for upcoming recurring transactions or budget overages.
